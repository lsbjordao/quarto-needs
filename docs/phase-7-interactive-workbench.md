# Phase 7 — Interactive graph workbench

Status: **six slices complete. First: the explorer's baseline comparison is now an interactive operation — the build publishes one compact overlay annotation artifact when a project has a comparison baseline; the `need-graph` page embeds it next to the projection; and a `graph-modes.js` client gives the reader a Catalog/Changes/Impact mode switcher plus an *Affected only* visibility toggle, all applied in place on the live graph. Every classification is Python's, pre-rendered into the artifact — the browser only presents. Proven on this project's own self-hosted example with a tracked historical baseline captured at the commit immediately before the Phase 6 C4 retrofit, so the Changes mode shows the model's real, recent evolution, verified in both languages through the full multilingual render gate and exercised live in a browser. Second: two-node semantic shortest path — descoped from the first slice (re-reading `build_impact_overlay` showed the impact view was already "affected-only by construction," so the mode switcher delivered analysis value with less new surface first), now delivered as a generalization of the existing `pathToRoot` client-side algorithm and its highlight styling, entirely client-side over the already-published bounded projection — no new Python computation, no new artifact. Third: deep-linking and saved exploration state — a new `graph-state.js` client that lets a hash-fragment link (or, absent one, a browser's own remembered `localStorage` state) reproduce the exact view — filters, traversal profile, search text, mode, affected-only, focused node, and any active path — restored by replaying the same inputs and events a reader would produce by hand, on the same controls every other client already owns. Fourth: the static accessible table now lists nodes' own attributes, not just edges — closing the gap between what the (deliberately `aria-hidden`) interactive canvas shows and what its documented non-JS/non-visual equivalent, the `.need-graph-table`, actually carried; canvas-level keyboard graph-traversal itself remains a separate, explicitly deferred decision, not an oversight. Fifth: breadcrumbs — a clickable trail rendered from the exact `pathToRoot`/`shortestPath` result already computed for the "Path to root"/"Path between…" buttons, shown only while a path is active (never guessing a root among several when none was asked for), letting a reader jump to any node on the shown path without losing it. Sixth: a fullscreen toggle for the whole workbench (controls + canvas + status, not just the canvas) — the Fullscreen API doesn't reparent anything, so breadcrumbs, active-path highlighting, and popups all survive the transition untouched; the only real effect is re-running the same resize/fit pair already used to recover from a 0-width init.**

## Why this reuses the overlay machinery instead of new derivation

Diff and impact overlays already existed as *build-time projection modes*: `build_diff_overlay`/`build_impact_overlay` annotate a bounded projection with `change` fields and explanation-path membership, and `graph.js` already colors added/removed/modified/relocated nodes and styles `pathMember` edges. What was missing was interactivity: `config.graph.mode` decided once per build which single view a reader ever saw.

The new artifact therefore adds **zero new derivation**. `build_graph_overlays` builds the *same* overlay projections the diff/impact modes would produce (same selection, limits, layout, seed) and extracts their annotations: diff change maps plus ghost nodes/edges, impact entries (id/origin/distance/path/classification) plus path-edge pairs plus ghosts. The artifact cannot disagree with what the overlays themselves show, because it is what they show — pinned by a falsification step that hardcodes a classification and watches the extraction test fail. Size is proportional to *what changed*, not to the graph (the self-hosted example's artifact is ~3 KB against a ~146 KB projection).

Transport is embed-not-fetch, the same choice the projection itself already made: `graph.lua` reads the sibling `<view-id>-overlays.json` file when it exists, validates it as JSON, and emits a second `<script type="application/json" data-need-graph-overlays>` tag. Its presence is the availability signal — no marker attribute to drift, no `resources` config, works over `file://`. No baseline means no artifact, no tag, no mode UI: graceful degradation verbatim from `build_default_projection`'s existing missing-baseline rule.

## What is implemented

- **`[graph] baseline` config key** — points the overlay artifact at a project's curated, tracked comparison baseline (default stays `.quarto-needs/baseline.json`). Deliberately fingerprint-neutral like every other `[graph]` key: it names a presentation artifact, not semantics.
- **The overlay artifact** (`need-graph-1-overlays.json`, `need-graph-overlays-v1`) — extracted from the built overlay projections, written atomically by `write_graph_overlays` from the same CLI step that writes the default projection. Ghost entries carry full public-node shapes and stay out of the live change maps.
- **The embed** — `graph.lua` emits the overlays script tag when the sibling file exists for the requested projection. Default view only: pages requesting named-query projections correctly get no tag (a declared non-goal).
- **`graph-modes.js`** (loaded after `graph-explore.js`) — the mode switcher, applied entirely in place: no dataset rebuild, no re-initialization of the context/explore enhancements.
  - **Changes mode** applies the published change maps to live elements, adds ghost nodes/edges (a ghost's cy id is its published id whenever free, so labels stay readable; ids are prefixed only on collision), forces ghosts visible through a dedicated slot, and drives the existing color-by-change facet. Announces counts ("Changes mode: 3 changed, 0 removed").
  - **Impact mode** marks explanation-path edges via the published path-edge pairs, annotates impacted nodes with distance/origin data, adds impact ghosts, and announces the impacted count. Distances and origins are announced on selection; popup-body enrichment is a named follow-on.
  - **Affected only** narrows visibility to the impacted set through the *existing* predicate owner: `graph-explore.js`'s `installPredicates` remains the single writer of `__needGraphNodeAllowed`/`__needGraphForcedNodes`, now composing two new slots (`__needGraphOverlayForcedNodes`, `__needGraphAffectedOnly`) that the modes client only flips, asking the owner to re-derive via an exposed `__needGraphReapplyPredicates` hook. Filters, root paths, and overlays intersect instead of clobbering each other.
  - **Empty-set discipline:** an empty impacted set means "nothing to filter", never "hide the whole graph" — the toggle disables itself when impact propagation is empty, and the affected-only slot is only ever published non-empty or null. Found during the live browser verification of this slice (the self-hosted example's part-of-only evolution legitimately has zero impact propagation) and pinned by its own contract test.
  - The "presents, never classifies" contract is pinned by a source test that fails if the client hardcodes any change classification; falsified by mutation.
- **Self-hosted adoption** — `examples/quarto-needs/baselines/quarto-needs.json` is a tracked historical baseline: the engineering graph exactly as it stood at `73c5ea0`, immediately before the C4 retrofit, following the Aegis book's curated change-intelligence precedent (README documents provenance; regeneration from the same commit with the same `SOURCE_DATE_EPOCH` is byte-identical, verified before committing). `[graph] baseline` points the artifact at it. The rendered Overview page's mode switcher shows the model's real Phase 6 evolution in both languages.
- **Two-node shortest path** (`graph-explore.js`) — a "Path between…" control alongside the existing "Path to root" one. Both now share one generic path-highlight mechanism (`pathNodes`/`pathEdges`/`pathActive`, the `need-root-path-node`/`need-root-path-edge` classes, forced visibility through the existing predicate owner) rather than two parallel systems; an `activePathKind` flag ("root"/"between") tracks which button owns the currently-displayed path so clearing/replacing behaves correctly regardless of which was clicked. The search is deliberately undirected within the active traversal-profile's allowed families — unlike `directParents`'s own parent-only walk (which follows each relation's declared `traversalDirection`), the new `neighbors()` helper treats every edge in an allowed family as traversable both ways, including `"none"`-direction relations (e.g. `references`) that a root-walk never follows at all — answering "are these two things connected", not "can you walk from one to the other along declared hierarchy." Picking the two endpoints reuses the existing node-focus event the rest of the client already emits: clicking "Path between…" enters a picking state (announced), and the *next* focus change is consumed as the second endpoint instead of triggering the ordinary "clear any active path" behavior every other focus change already has — the one real new state-machine wrinkle, since without it the second pick would immediately erase the first. The same node picked twice yields the trivial one-node, zero-edge path; no connection announces the failure the same way "no path to a root" already does.
- **Deep-linking and saved exploration state** (`graph-state.js`, extension version 0.1.7, loaded last) — captures the filters, traversal profile, search text, mode, affected-only toggle, focused node, and active path (root or between) as one JSON object per graph instance, keyed by the container's own `id` (already the shortcode's `instance_id`, so it doubles as a normal anchor-scroll target when no state follows it). Multiple `need-graph` embeds on one page each get their own key inside the same hash, `#need-graph-1=...&decision-view=...`, so restoring or persisting one never touches another. Restoration replays the exact inputs a reader would produce — setting a `<select>`'s value and dispatching `change`, checking a box and dispatching `change`, dispatching the same `quarto-needs-node-focus` event `graph-context.js` itself dispatches on a real tap, clicking the path buttons — rather than exposing a second state API the other clients would need to stay in sync with. The one genuinely new surface is `container.__needGraphActivePath`, set wherever `graph-explore.js` already tracks `pathActive`/`activePathKind`, so the state client can read which path (if any) is showing without reaching into that module's private closure. A shared link always wins over a saved one on load (per an explicit product decision, not a default); either is written via `history.replaceState`, never `pushState`, so exploring a graph never spams browser history; writes are debounced 400ms since the search box fires on every keystroke; and the existing "Reset" control now also clears both the hash and the saved copy for that instance, so a manual reset can't be silently undone by state that link or storage still remembers.
- **Breadcrumbs** (`graph-explore.js`) — a `.need-graph-breadcrumbs` trail rendered by `renderBreadcrumbs(nodes)` from the exact same `result.nodes` array already stored on `container.__needGraphActivePath` at the two points that set it (the "Path to root" success and the "Path between…" second-pick success) — no second, separately-maintained copy of path data, no new traversal. Shown only while a path is active, by explicit choice: computing and displaying a root breadcrumb on every focus change would have to silently pick one root among several whenever a node has multiple parents, which would mislead rather than inform; showing the trail only for an already-computed, user-requested path sidesteps that ambiguity entirely. Each entry is a button showing the node's id; clicking one re-focuses that node through the exact same `quarto-needs-node-focus` event a canvas tap already dispatches, rather than a second, parallel navigation mechanism. This surfaced one real behavior gap worth fixing on its own: every focus change previously cleared any active path unconditionally, including a re-tap of a node the path already highlights — which would have made clicking a breadcrumb entry immediately erase the very trail just clicked. Fixed by a narrow, principled rule in the shared focus listener: a focus change is only treated as "leaving the path" when the newly focused node is *not already a member of the currently active path* — re-focusing a path member (breadcrumb click or canvas re-tap alike) just moves attention within the same trail. `clearPath()` clears the breadcrumb bar alongside everything else it already resets.
- **The static accessible table now lists nodes, not just edges** (`graph.lua`'s `node_table_rows`, mirrored by a Python `node_table_rows`/`NodeRow` in `graph_render.py` for the same golden-fixture/potential-export path every other table-shaped helper in that module already serves — the two are hand-synchronized, like the existing `mermaid_source`/`edge_table_rows` pair, since the Lua side is what actually drives the rendered page and the Python side does not call into it). Investigating this slice found that the interactive canvas is deliberately `aria-hidden` (`graph.js` sets it explicitly, with a comment naming the static table as the primary operable representation for keyboard/screen-reader readers) — so the real, load-bearing gap was not the canvas's own ARIA role but that its documented accessible equivalent had not kept pace: the table listed every edge's relation/change/impact but never a node's own type, status, priority, or tags, which were otherwise visible only on the canvas that non-visual readers are explicitly routed away from. The new table is inserted immediately before the existing edge table, in both languages the multilingual render gate covers, with the same column set as the Python `NodeRow`. This slice does **not** give the interactive canvas itself keyboard focusability or arrow-key traversal — that remains a separate, harder, explicitly deferred problem (see Known limitations item 4), not something this slice silently left half-done.
- **Fullscreen** (`graph.js`) — a `.need-graph-fullscreen` button in the controls bar, server-rendered by `graph.lua` next to Fit/Reset (matching their static-markup pattern, unlike graph-explore.js's JS-inserted controls, since this is core canvas plumbing owned by the same file that already manages `cy` sizing). It toggles `.need-graph-container` — controls, canvas, and status together, not just the canvas, so search/filters/mode-switcher/path buttons/breadcrumbs stay usable while fullscreen — via `container.requestFullscreen()`/`document.exitFullscreen()`, checked against `document.fullscreenElement === fullscreenRoot` so multiple `need-graph` instances on one page never fight over shared state. A single `fullscreenchange` listener (fires uniformly whether exit came from the button, Escape, or browser chrome) re-runs the exact `stabilize()` (`cy.resize()` + `cy.fit()`) pair already used to recover from a 0-width init at load — no new resize logic. `requestFullscreen()` does not reparent the element, only how it is painted, so every other module's state (breadcrumbs, active-path highlighting, popups) survives the transition with zero special-casing; the accessible static table sits outside `.need-graph-container` in the DOM already, so it is simply not part of the fullscreen view. Missing `requestFullscreen` support (old browser, restrictive iframe policy) removes the button entirely rather than leaving a dead control; a rejected request (e.g. blocked by a Permissions Policy) is caught and announced ("Fullscreen unavailable") rather than crashing. CSS sizes the canvas by flex-growing into whatever room the controls/status leave inside `.need-graph-container:fullscreen`, rather than a pixel `calc()` that would need to track however tall the wrapping controls bar happens to be.

## What was learned

- The live browser verification earned its keep: exercising the switcher on the real example exposed the empty-impacted edge case (a part-of-only evolution has real Changes but legitimately zero Impact propagation) — checking "Affected only" there would have blanked the whole graph. The guard is now a contract test plus a visible disabled state.
- The artifact-from-built-projections design proved its worth immediately: when the extraction initially mapped ghosts into the live change maps too, the distinction (live annotations vs. ghost elements) was corrected in one place with the tests reading the built views, not re-specifying diff semantics.
- The fixture grammar detail worth remembering: relation attributes are authored as `verified-by: TC-1` preamble lines or quoted opening-line attributes — a `verified-by="TC-2"` *body* line parses as neither and silently produces no relation.

## Known limitations (explicit, not silent)

1. **The static `.need-graph-table` stays the catalog table in every mode.** Rather than duplicate the Lua table builder in JS, non-catalog modes label honestly via announcements; popups carry live annotations. A JS table re-render is the named follow-on.
2. **Overlays cover the default view only** — named-query projections have no variants and their pages show no switcher. Follow-on if needed.
3. **Impact-mode node popups are not enriched** with distance/path/classification rows; the data is on the node and announced on selection. Follow-on.
4. **The interactive canvas itself is still not keyboard-focusable or arrow-key-navigable.** It stays deliberately `aria-hidden`, with the accessible static table (now covering both nodes and edges) as the documented equivalent path — a decision made explicitly during that slice's own brainstorming, not an unaddressed gap. Full keyboard-driven graph traversal (arrow keys between adjacent nodes, spatial navigation of a force-directed layout) is a substantial UI-accessibility problem in its own right and is left as a future, separately-scoped decision. Export and mini-map remain unbuilt.
5. **Breadcrumbs only appear while a path is active** — there is no ambient "where am I from some root" trail on every focus change, by deliberate choice (see above). A reader who wants a trail must first click "Path to root" or complete a "Path between…" pick.
6. **Fullscreen's transient "Exit fullscreen" label is English-only**, matching this file's existing dynamic status strings (e.g. "Graph reset") rather than introducing new i18n plumbing for one button; the initial, resting label still comes from Lua's own `views.tr()` and is restored correctly on exit.
7. **Verification boundary, stated honestly:** mode switching, announcements, recoloring, and the empty-impact disabled state were exercised live in a browser; synthetic clicks on the small checkboxes do not register in this automation environment (pre-existing controls such as "Fixed spacing" behave identically), so the affected-only *checked* path is pinned by source contracts and the rendered disabled/enabled states rather than an automated end-to-end click. The shortest-path slice was verified differently and more directly: its two new pure functions (`neighbors`/`shortestPath`) were extracted from the real file and executed against a hand-built fake graph exercising cross-family paths, family-restricted blocking, the trivial same-node case, a disconnected node, and a `"none"`-direction relation. The deep-linking slice got the same treatment: its hash/storage read-write-clear functions were extracted and run against fake `location`/`history`/`localStorage` globals, proving multi-instance isolation (writing a second graph's state never disturbs the first), hash-over-storage precedence, `replaceState`-not-`pushState`, and that malformed percent-encoded content degrades to `null` rather than throwing. The breadcrumb slice got the same treatment: `renderBreadcrumbs` was extracted and run against a fake `document`/container, proving it clears and hides on a null/empty path, renders buttons and separators in `result.nodes`' own order for a multi-node path, and that clicking an entry sets `__needGraphFocusNode` and dispatches the exact shared focus event with the clicked id; the focus listener's new path-membership skip was extracted and run against fake path state, proving `clearPath` is skipped only when the focused node is already a path member, and still runs otherwise (no path active, or a genuinely different node). The fullscreen slice got the same treatment: the click handler and `fullscreenchange` listener were extracted and run against a fake `document`/button/container exposing a controllable `fullscreenElement` and a `requestFullscreen` that can resolve or reject — proving the feature-detection removal, the toggle correctly checking *this* graph's own container (not a global flag), the label restoring to its original (Lua-provided) text on exit rather than a hardcoded string, `stabilize()` running on both the enter and exit transitions, and a rejected request being caught and announced without ever leaving `fullscreenElement` set. In all these cases this is genuine runtime verification of the actual shipped code, not a re-implementation, and not just a source-pattern check — but the click-driven UI itself (the path-picking state machine, the restore-on-load sequence, breadcrumb clicks, the fullscreen transition) was not exercised in a live browser, for the same automation-environment reason as this item's own checkboxes.
8. **`build_graph_overlays` always computes both diff and impact overlays** on every scan that has a configured baseline, regardless of `[graph] mode` — duplicating a traversal `build_default_projection` may already have performed for the plain catalog view. Correctness is unaffected (each overlay is still exactly what its own builder would produce), but a project with a large graph and `[graph] mode = "diff"` pays for the diff overlay twice plus an impact overlay it may never use, purely to keep the browser-side mode switcher populated. Left unfixed for now — sharing the already-computed selection between the catalog path and the overlay artifact needs a small interface change to `build_default_projection`/`write_graph_overlays`, which is worth doing deliberately rather than folding into a post-hoc bug-fix pass.

## Post-implementation review findings (fixed)

A multi-angle automated review after this slice landed found and fixed three real defects, none caught by the existing test suite because none of them are exercised by the "everything succeeds, nothing exceeds a limit, every id exists" path every existing test takes:

- **`graph-modes.js`'s `findEdge` returned `null` on a miss, but both call sites checked `.length`** (a Cytoscape-collection method, not something a plain `null` has) — `null.length` throws inside `cy.batch()`, so a `diff.edges`/`impact.pathEdges` entry referencing an edge absent from the live catalog graph (plausible: the overlay is built from a separate traversal than the rendered projection) would abort the whole mode-apply mid-way, leaving ghosts added but predicates never reapplied. Fixed to a plain truthiness check; pinned by a source test.
- **`write_graph_overlays` only caught `BaselineError`**, so a `GraphLimitExceeded` from the overlay's own diff/impact traversal (not the same selection as the plain catalog view, so it can exceed budget even when the catalog comfortably fits) propagated uncaught and crashed the whole `quarto-needs scan`. Fixed to degrade the same way a missing baseline already does — no artifact, no failed build — matching the graceful-degradation contract every other optional presentation artifact in `graph_output.py` already honors. Pinned by a test that forces the overlay traversal over a tiny configured budget.
- **The "Affected only" checkbox's own `change` handler called `reapplyPredicates()` but never `contextApi.refresh()`**, unlike every other place that mutates the same predicate slots (the mode-select handler, the context-reset handler), both of which call `syncSlots()` (predicates + refresh together). The slot and status text updated but the canvas kept showing every node until an unrelated action happened to trigger a refresh. Fixed to call `syncSlots()`; pinned by a source test isolating the handler's own body.

A `touched.ghostEdgeIds` field (declared, cleared, never populated or read) was also removed as dead state.
