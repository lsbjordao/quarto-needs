29  Verificação executável e evidência de máquina

O Quarto-Needs distingue três afirmações que frequentemente são confundidas:

  1. um requisito declara uma obrigação de engenharia;
  2. um caso de teste modelado declara como essa obrigação é verificada;
  3. a evidência de máquina registra qual teste executável realmente rodou e se seu vínculo concorda com o modelo de engenharia.

Essa distinção evita que uma suíte de testes verde seja automaticamente tratada como prova de um requisito não relacionado.

29.1 Vincule testes pytest a objetos de engenharia

O plugin pytest do Quarto-Needs fornece dois markers:

import pytest

@pytest.mark.requirement("FUN-004")
@pytest.mark.quarto_need_test_case("TC-010")
def test_graph_exploration_assets():
    ...

requirement identifica as obrigações de engenharia reivindicadas pelo teste executável. quarto_need_test_case vincula o nó pytest a um ou mais objetos test-case modelados.

O modelo deve carregar o vínculo executável recíproco:

::: {.need #TC-010 type="test-case" status="passed"
      pytest-nodeid="tests/test_graph.py::test_graph_exploration_assets"
      evidenced-by="EVD-010"}
## Regressão da exploração interativa do grafo
...
:::

O node ID estável do pytest é uma referência física de execução. Ele não substitui o caso de teste modelado, que continua sendo o objeto de verificação de engenharia.

29.2 Gere evidência determinística do provider

A escrita do artefato é opt-in. Execuções pytest comuns não possuem efeitos colaterais de arquivos do Quarto-Needs.

pytest \
  --quarto-needs-evidence=.quarto-needs/evidence/pytest-provider.json

O mesmo destino pode ser fornecido por QUARTO_NEEDS_PYTEST_EVIDENCE.

O artefato versão 1 do provider é validado por schemas/evidence-pytest-v1.schema.json e contém dados semânticos determinísticos da execução:

{
  "provider": "pytest",
  "schemaVersion": "1",
  "tests": [
    {
      "nodeid": "tests/test_graph.py::test_graph_exploration_assets",
      "outcome": "passed",
      "requirements": ["FUN-004"],
      "testCases": ["TC-010"]
    }
  ]
}

A evidência v1 expõe intencionalmente apenas passed, failed e skipped. A semântica mais rica de expected failures do pytest é normalizada de forma conservadora: XFAIL permanece skipped, enquanto qualquer XPASS é registrado como failed, inclusive XPASS não estrito que o pytest possa reportar como teste aprovado. Assim, uma passagem inesperada não se transforma silenciosamente em evidência positiva de engenharia.

Timestamps e durações são excluídos intencionalmente do payload do provider para que resultados de engenharia idênticos permaneçam reproduzíveis.

29.3 Envelope de atestação neutro em relação ao provider

A proveniência da execução pertence a um envelope separado e neutro em relação ao provider, definido por schemas/evidence-envelope-v1.schema.json. Isso preserva o payload determinístico do provider enquanto o vincula a um estado concreto do modelo de engenharia.

Crie uma atestação a partir de um payload do provider com:

quarto-needs --root . evidence attest \
  .quarto-needs/evidence/pytest-provider.json \
  --output .quarto-needs/evidence/pytest.json \
  --expires-hours 24

--source-revision pode ser fornecido explicitamente. No GitHub Actions, GITHUB_SHA é capturado automaticamente quando nenhuma revisão explícita é informada.

O envelope registra:

  • nome e versão do provider;
  • timestamp generatedAt e, opcionalmente, expiresAt;
  • revisão de origem opcional;
  • fingerprints atuais de configuração, grafo semântico e representação;
  • schema do artefato do provider;
  • digest SHA-256 canônico do payload embutido;
  • o próprio payload do provider.

Conceitualmente:

{
  "schemaVersion": "1",
  "kind": "quarto-needs-evidence",
  "provider": {"name": "pytest", "version": "8.0"},
  "generatedAt": "2026-08-30T12:00:00Z",
  "expiresAt": "2026-08-31T12:00:00Z",
  "subject": {
    "sourceRevision": "abc123",
    "configurationFingerprint": "...",
    "semanticGraphFingerprint": "...",
    "representationFingerprint": "..."
  },
  "artifact": {
    "schema": "evidence-pytest-v1",
    "digest": "sha256:...",
    "payload": {"provider": "pytest", "schemaVersion": "1", "tests": []}
  }
}

O envelope é intencionalmente provider-neutral. O pytest é o primeiro provider executável, enquanto evidence-checks-v1 fornece um payload determinístico comum para adapters de JUnit XML, coverage.py, Quarto render, JSON Schema, lint e type-check.

O digest do payload é validado antes da verificação semântica. Portanto, um payload modificado não pode continuar reutilizando silenciosamente uma atestação antiga.

29.4 Valide a evidência contra o modelo atual

A geração é apenas metade do contrato. O mesmo comando valida artefatos crus de provider e envelopes atestados contra o grafo canônico de engenharia:

quarto-needs evidence check .quarto-needs/evidence/pytest.json

Para consumidores de máquina:

quarto-needs evidence check \
  .quarto-needs/evidence/pytest.json \
  --format json

O comando permanece retrocompatível com evidence-pytest-v1 cru. Ele também reconhece evidence-checks-v1 cru ou atestado. Quando recebe uma atestação, valida a proveniência contra o snapshot atual.

A verificação semântica do pytest confirma que:

  • todo teste executável passou;
  • toda entrada de evidência está vinculada a um caso de teste modelado;
  • todo caso de teste referenciado existe;
  • seu pytest-nodeid modelado é igual ao node ID executável;
  • todo requisito referenciado existe;
  • todo requisito reivindicado pelo teste executável está realmente conectado por relação da família de verificação a um caso de teste modelado vinculado;
  • reciprocamente, todo requisito que o modelo declara como verificado por um caso de teste vinculado é reivindicado pelo teste executável;
  • todo caso de teste modelado que possui pytest-nodeid está presente no artefato.

Para evidência atestada, também são verificados:

  • fingerprint de configuração;
  • fingerprint do grafo semântico;
  • fingerprint da representação;
  • generatedAt válido e não futuro;
  • expiresAt, quando presente, ainda válido e posterior a generatedAt;
  • quando GITHUB_SHA está disponível, concordância entre sourceRevision atestada e a revisão corrente do CI.

Assim, a cadeia passa a incluir também o estado exato do grafo que a execução pretende provar:

requisito --verified-by--> caso de teste modelado
                              │
                              │ vínculo de execução
                              ▼
                         provider executável
                              │
                              ▼
                    payload determinístico
                              │ SHA-256 + fingerprints do grafo
                              ▼
                   atestação provider-neutral

29.5 Diagnósticos de evidência

EVD001 precede todos eles: reporta um artefato pytest cujo array tests está ausente ou malformado. Como nenhum check pôde ser interpretado, nenhum diagnóstico EVD1xx é produzido junto dele.

Os diagnósticos específicos do pytest usam códigos EVD1xx:

Código Significado
EVD101 resultado executável diferente de passed
EVD102 teste executável sem vínculo com caso de teste modelado
EVD103 evidência referencia caso de teste desconhecido
EVD104 caso de teste modelado não possui pytest-nodeid
EVD105 node IDs pytest modelado e executável divergem
EVD106 evidência referencia requisito desconhecido
EVD107 teste executável reivindica requisito não verificado pelo caso de teste vinculado
EVD108 caso de teste modelado vinculado ao pytest está ausente do artefato
EVD109 caso de teste modelado verifica requisito que o teste executável não reivindica

Os diagnósticos neutros de atestação usam EVD2xx:

Código Significado
EVD201 atestação sem subject válido
EVD202 fingerprint de configuração obsoleto
EVD203 fingerprint do grafo semântico obsoleto
EVD204 fingerprint de representação obsoleto
EVD205 revisão de origem difere da revisão esperada
EVD206 generatedAt inválido
EVD207 evidência declara ter sido gerada no futuro
EVD208 evidência excede idade máxima fornecida por um chamador
EVD209 expiresAt inválido
EVD210 evidência expirada
EVD211 expiresAt anterior a generatedAt

A validação genérica de machine checks usa diagnósticos EVD3xx; veja Providers de evidência de máquina.

EVD107 e EVD109 formam a barreira recíproca de rastreabilidade: juntos exigem concordância entre os markers executáveis e as relações de verificação do modelo, em vez de aceitar qualquer uma das fontes isoladamente como autoridade suficiente.

Artefatos malformados, não suportados ou com digest inválido são erros de uso/artefato e retornam código 2. Falhas de I/O retornam 3. Um artefato estruturalmente legível que diverge do modelo de engenharia, ou cuja atestação esteja obsoleta, retorna 1.

29.6 Exemplo autocontido

O estudo de caso autocontido do Quarto-Needs exercita o fluxo completo diretamente:

make evidence-self-example

Esse alvo:

  1. executa testes reais representativos de governança de ADR, segurança do grafo público, views nomeadas e análise de impacto;
  2. grava o artefato determinístico do provider em examples/quarto-needs/.quarto-needs/evidence/pytest-provider.json;
  3. cria uma atestação com validade de 24 horas em examples/quarto-needs/.quarto-needs/evidence/pytest.json, incluindo GITHUB_SHA automaticamente no CI;
  4. valida a atestação contra o grafo de engenharia autocontido atual.

make render-self-example depende desse alvo, portanto o exemplo não pode ser renderizado com sucesso quando houver fingerprints obsoletos, atestação expirada, revisão de CI divergente ou vínculos executáveis inconsistentes.
