# Phase 6 — Architecture model and C4 projections (first slice)

Status: **complete for the planned first slice — `actor`/`external-system`/`system`/`container` are first-class typed objects alongside `component`/`source-module`; `part-of` exists as `decomposes`'s genuine inverse; the ARC001 structural rule enforces layer adjacency; and Mermaid C4 Context/Container/Component diagrams plus a plain Code-level table are generated as projections of the same engineering graph — pre-rendered by the Python CLI, read by a thin Lua shortcode, with zero new selection or rendering algorithm. The slice is proven end to end by retrofitting this project's own architecture into the hierarchy: `SYS-QUARTO-NEEDS` with an actor, two external systems, two containers, all 8 components and all 15 source-modules linked by `part-of`, and three generated C4 views embedded in the self-hosted example (mirrored in pt-BR), verified through a real `quarto render`.**

C4-like views are **projections of the same engineering graph**, not a second architecture database. Nothing in this phase forks the model: every new type is a normal citizen of `config.py`'s type validation, the new relation is a normal `relations.py` catalog entry, the new structural rule is a normal `rules.py` evaluator, and every diagram is derived from the same snapshot the requirements/decisions/risk/test/evidence views already consume.

## Why this reuses the existing graph machinery instead of new mechanism

The whole design reduces to two observations. First, a C4 view at any level is just *one focus object plus one level of its `part-of`/`decomposes`/`depends-on` neighborhood* — exactly what `graph_projection.py`'s `select_graph(seeds=(focus,), depth=1)` already computes, differing only in which relations are allowed and what type the focus must be. Second, rendering is static text generation from an already-computed projection, which is exactly the role `graph_render.py`'s `mermaid_source()` already plays. `c4_projection.py` and `c4_render.py` are therefore thin, validated wrappers over existing machinery — no new traversal, no new layout, no C4-specific graph code.

The Python/Lua boundary stayed where the project's binding invariant put it: **Python remains the sole semantic authority; Lua only presents.** `c4.lua` never interprets a projection, never maps a type to a Mermaid macro, never decides what a boundary is — it reads a pre-rendered text file and hands it to the existing `mermaid_inline_svg` helper. This is a deliberate correction from the original spec, which had assumed Lua would do the type→macro mapping; pre-rendering the text in Python made the Lua side a pure reader and kept every C4 decision testable in pytest.

`part-of` deliberately got its own `v1_name` rather than sharing `decomposes`' (unlike `derives-from`/`derived-from`, which correctly share one): the two directions have *swapped* source/target roles, so a per-direction `relation_policies` entry must be able to target one authoring direction without silently also matching the other. `implements`/`implemented-by` is the pattern that was followed. The relation catalog version bumped to `"4"`, the rule-set version to `"7"`.

## What is implemented

- `part-of` relation (`relations.py`) — `decomposes`'s missing inverse: `part-of` runs child→parent with roles `(part, whole)`, `semantic_family == "decomposition"`, `inverse_v1_name` pairing in both directions. A child can now self-declare containment instead of requiring the parent to enumerate it.
- ARC001 layer-adjacency rule (`rules.py`) — always-error (mirroring `DEC005`'s severity policy: a layer skip is a structural contradiction, not a tunable style preference). `part-of`/`decomposes` must connect a layer to the one exactly above it in the fixed order `system > container > component > source-module`; types outside the C4 layer set (`actor`, `external-system`, project-specific types) are simply never matched by the layer table — the rule neither passes nor fails them. Both authored directions are handled explicitly. Falsified by gutting the adjacency check.
- `PublicNode.technology` (`graph_projection.py`) — a narrow, named pass-through from the object's `technology` attribute (non-empty strings only, `None` otherwise, omitted from `to_dict()` when absent — the same conditional-inclusion pattern the `change` field already used). Mermaid's `Container()`/`Component()` macros take an optional technology label, and nothing in the public projection carried it. The JSON schema and every construction path gained matching coverage.
- `build_c4_view` (`c4_projection.py`) — one generic operation, three level configurations: `context`/`container` require a `system` focus, `component` requires a `container` focus; each level is a `select_graph` depth-1 call over its relation allowlist (`context` sees only `depends-on` interactions; `container`/`component` add the containment relations). Unknown focus, wrong focus type, and unsupported levels each raise a distinct `C4ViewError`.
- `c4_mermaid_source` / `c4_code_table_markdown` (`c4_render.py`) — Context renders the system as an opaque box with its actors/external systems beside it; Container/Component render the focus as a `System_Boundary`/`Container_Boundary` with its children inside; `depends-on` edges become `Rel()` interaction arrows. Identifiers are hex-encoded with a `c4_` prefix and labels are escaped against Mermaid syntax (falsified by no-op'ing the escaper). The Code level is not a diagram: Mermaid has no C4-Code type and source-modules carry no inter-module arrows, so it renders as a plain Markdown table (ID / Path / Language / Implements) of the component's direct `source-module` children instead of forcing diagram syntax onto non-diagram content. Both the boundary-grouping logic and the table's child discovery handle *both* authored directions — the first execution pass only checked `part-of` and silently would have dropped every `decomposes`-authored hierarchy (caught in review, fixed with its own test).
- `write_c4_projections` (`graph_output.py`) — pre-renders one JSON file per view into `.quarto-needs/graphs/`: every `system` gets `c4-context-<id>.json` and `c4-container-<id>.json`; every `container` gets `c4-component-<id>.json`; every `component` gets `c4-code-<id>.json` (the table). Files carry `{"schemaVersion": "c4-view-v1", "kind": "mermaid"|"table", "source": ...}`; stale `c4-*.json` files are removed before writing. Auto-derived, not configured — unlike named queries, nothing for a project to declare and nothing that can drift out of sync with the graph. No manifest: the id is deterministic (`c4-<level>-<object id>`), constructed identically by the Lua reader. Wired into the same CLI build step that already writes the general graph projections.
- the `need-c4` shortcode (`_extensions/quarto-needs/c4.lua`) — `{{< need-c4 root="<id>" level="context|container|component|code" >}}`. A thin reader: loads the pre-rendered JSON, renders `kind: "mermaid"` sources inline as SVG (gated on HTML output format — the first pass unconditionally inlined raw HTML and would have corrupted non-HTML writers; the fix added the format gate plus a PNG-asset fallback path, mirroring `need-graph`'s behavior) and `kind: "table"` sources as real Markdown blocks. A missing view warns instead of failing the render.
- self-hosted retrofit (`examples/quarto-needs/`) — config registers `actor`/`external-system`/`system`/`container` (containers require `technology`) and a `part-of` policy (`allowed-*` types plus `maximum-per-source = 1` — the existing generic REQ010 mechanism, no new validation code). `architecture.qmd` adds `SYS-QUARTO-NEEDS` (system), `ACTOR-ENGINEER` (actor, `depends-on` the system), `EXT-GITHUB` and `EXT-OSLC` (external systems already implied by the Phase 5/5.5 federation work but never modeled as boxes), and `CONTAINER-PYTHON-PKG`/`CONTAINER-QUARTO-EXT` — splitting the 8 existing components by actual deployable unit (Python package vs. Quarto extension bundle); every component and every one of the 15 source-modules in `implementation.qmd` gained its `part-of` edge, closing a link that previously existed only as this documentation's own section-heading convention. `architecture.qmd` embeds three `need-c4` views (Context + Container of the system, Component view of the Python package), mirrored in pt-BR with translated prose and identical canonical relations/attributes — the first real end-to-end proof, rendered through the project's own pre-render + `quarto render` pipeline and confirmed present as distinct SVGs in the built HTML.

## What was learned

- The retrofit itself was the design's real test. Authoring `part-of` from the child's side turned out to be the direction the content naturally wants (every component knows its container; the container shouldn't have to enumerate them), and handling *both* directions in every consumer — ARC001, the boundary grouping, the Code table — stopped being defensive the moment both `part-of` and legacy `decomposes` authoring had to keep working.
- Two defects were caught by the plan's own verification discipline rather than by luck: the Code-table/boundary logic silently ignoring `decomposes`-authored children (added tests for the second direction), and `need-c4` unconditionally emitting raw HTML (the real-`quarto render` test in a non-HTML-safe path exposed the format gate + PNG fallback need).
- The pre-render/reader split paid for itself immediately: gating SVG inlining on output format, adding the PNG fallback, and rendering tables as Markdown were all one-side changes to Lua presentation code; nothing in Python moved.

## Known limitations (explicit, not silent)

1. **No relation-attribute authoring syntax.** The `.need`-block parser grammar has no syntax for inline per-relation attributes, so the spec's assumed `depends-on: TARGET technology="..."` cannot be authored. Interaction arrows therefore always carry the relation's fixed catalog label ("Depends on"). A follow-on slice can add relation-attribute authoring once there is a second consumer that needs it — it is a cross-cutting parser change affecting every relation, deliberately not smuggled into this phase.
2. **Interaction edges reach the focus node only, not its children.** A Container-level view shows actors/external systems connected to the system as a whole, never to a specific container two hops away. This keeps "one generic operation" literally true (`select_graph(seeds=(focus,), depth=1)`); revisit when the example's content actually has container-specific interactions.
3. **"Exactly one parent" is only half-enforced by the generic mechanism.** REQ010's `maximum-per-source = 1` catches duplicate parents; its `minimum-per-source` only inspects objects that already have *some* `part-of` edges, so an object with zero parents is invisible to it (a pre-existing property of the mechanism, confirmed by reading `_cardinality` directly). The retrofit's own completeness is pinned exactly where it belongs — `test_self_hosted_c4_part_of_ownership_is_complete_and_exact` asserts all 23 ownership tuples exactly — and the doc-level claim is deliberately "duplicates rejected", never "orphans impossible".

## What is intentionally not implemented yet

Dynamic and deployment C4 views follow only after the static hierarchy is stable, per the roadmap's own sequencing — and this first slice exists to make it stable. The relation-attribute authoring grammar is named above as the follow-on it needs. Nothing else from the C4 idea set (styles, legends, interactive drill-down between levels) is guessed at here; each is its own reviewed slice once there is real content that needs it.
