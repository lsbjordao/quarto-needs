# Phase 8B — Extension-First Distribution and Managed Engine Implementation Plan

> **For agentic workers:** implement task-by-task with TDD and independent review. Preserve the repository's established semantic-kernel boundary. Do not broaden this phase into unrelated feature work.

**Date:** 2026-09-02  
**Spec:** `docs/superpowers/specs/2026-09-02-extension-first-distribution-design.md`  
**Roadmap:** Phase 8 — release hardening  
**Goal:** Make the active Quarto extension provision and invoke its exact Python semantic engine automatically, eliminating the user's separate `pip install` and manual `project.pre-render` steps.

## Prerequisites

1. Work from current `main`.
2. Do not mix this phase with an unfinished migration of the C4 renderer boundary. If Phase 6B still has legacy and new C4 writers being actively changed, finish that slice first or isolate this work on its own branch.
3. Preserve all currently supported CLI behavior.
4. Use the existing full test suite as the semantic regression oracle.
5. Do not depend on GitHub Actions being available; every task must have a meaningful local verification path.

## Global constraints

- Python remains the only semantic authority.
- Lua remains presentation-only.
- `bootstrap.py` is runtime plumbing, not a second parser.
- No global `pip install`.
- No `sudo`.
- No PATH mutation required for ordinary rendering.
- No silent use of a system `quarto-needs`.
- No unpinned `latest` installation.
- Managed engine version must equal extension version exactly.
- A bootstrap failure fails the Quarto render.
- No semantic artifact bytes may change solely because the engine is invoked through the extension rather than through the CLI.
- Every committed checkpoint must leave the full relevant suite green.
- Real Quarto integration tests are required; manifest-text assertions alone are insufficient.
- Keep the declared `quarto-required: ">=1.6.0"` only if exact 1.6.0 integration proves it.

## Task 3 — Implement the standard-library managed-runtime bootstrap

### Files

- Create: `_extensions/quarto-needs/bootstrap.py`
- Create: `tests/test_extension_bootstrap.py`
- Modify: `tests/test_packaging.py` or equivalent version-contract tests

Do **not** wire the bootstrap into `_extension.yml` yet.

### Goal

Build and fully test the bootstrap before every real render starts executing it.

### Required bootstrap components

Factor the script into small standard-library functions covering:

```text
extension version
Python prerequisite
project root
runtime identity
runtime path
installed marker
runtime validation
exclusive lock
staging directory
provision command
engine import
canonical pre-render invocation
```

Keep the file importable by pytest without side effects.

Use:

```python
if __name__ == "__main__":
    raise SystemExit(main())
```

for execution.

### Runtime directory

Use identity dimensions sufficient to prevent an incompatible target install from being reused, for example:

```text
.quarto-needs/runtime/
  0.2.0/
    cpython-313-linux-x86_64/
```

Do not blindly use only engine version.

### Marker

Write `installed.json` only after a complete installation.

The marker must include:

- schema version;
- engine version;
- interpreter implementation;
- interpreter version/tag;
- platform;
- machine.

### Validation

A runtime is valid only when:

1. marker identity matches;
2. its site-packages directory exists;
3. `quarto_needs` can be loaded from that runtime;
4. `quarto_needs.__version__` exactly matches the extension version.

A marker alone is never proof.

### Lock

Use a cross-platform filesystem lock built with stdlib primitives.

Required tests:

- normal acquire/release;
- second process cannot acquire simultaneously;
- stale lock recovery;
- exception releases lock;
- staging directory cleaned after failure.

Do not rely on Unix-only `flock`.

### Commit

At the end of this task the script exists but no Quarto render invokes it automatically.

Suggested message:

```text
feat: add the extension managed-runtime bootstrap
```

## Task 4 — Provision the exact engine into generated project state

### Files

- Modify: `_extensions/quarto-needs/bootstrap.py`
- Extend: `tests/test_extension_bootstrap.py`

### Default installation

When runtime is absent, invoke the same Python interpreter:

```text
sys.executable -m pip
```

with an empty `--target` staging directory.

Default package spec:

```text
quarto-needs==<extension-version>
```

Do not use:

```text
pip
pip3
quarto-needs
```

as bare commands.

### Development/offline override

Implement:

```text
QUARTO_NEEDS_ENGINE_SOURCE
```

Rules:

- unset → install exact published package;
- set → value must resolve to a local filesystem package source;
- reject a missing path;
- do not interpret it as shell;
- do not accept a remote URL in this slice;
- after installation, verify actual imported package version exactly.

This override is how local integration tests provision current source without first publishing it.

### Installation algorithm

```text
acquire lock
    ↓
recheck runtime after lock
    ↓
create unique staging directory
    ↓
pip install --target staging/site-packages
    ↓
validate actual installed version
    ↓
write installed.json in staging
    ↓
atomically publish final runtime
    ↓
release lock
```

Never install into the final directory directly.

### Package-manager constraints

Use non-interactive pip invocation.

Do not:

- upgrade global pip;
- write user site-packages;
- create a global venv;
- modify the active interpreter;
- persist credentials.

### Failure tests

Cover at least:

- `pip` unavailable;
- install subprocess nonzero;
- requested package unavailable;
- wrong installed engine version;
- staging cleanup;
- existing valid runtime causes zero pip invocations;
- corrupted runtime is not trusted.

### Suggested commit

```text
feat: provision the exact engine into project-local runtime
```

## Task 8 — Harden update, corruption, and concurrency behavior

### Files

- Extend bootstrap tests
- Extend installed-path integration tests

### Required scenarios

#### Extension update

Simulate:

```text
extension 0.2.0 → runtime 0.2.0
extension 0.2.1 → runtime 0.2.1
```

Assert no in-place mutation of the old runtime.

#### Corruption

Delete or alter required managed runtime content.

Expected:

```text
runtime rejected
safe reprovision attempted
```

not:

```text
undefined import behavior
```

#### Concurrent bootstrap

Start two bootstrap processes against the same clean project.

Assert:

- no partial runtime;
- no duplicate final publication;
- both eventually get a valid runtime or one receives a bounded actionable failure;
- no corrupt marker.

#### First-run offline

No runtime + package source unreachable.

Assert failure text names:

- required engine version;
- missing runtime;
- provisioning failure;
- recovery action.

#### Python version

Test the version predicate separately.

The user-facing error must state the required minimum.

#### No pip

Test detection and message.

Do not attempt global `ensurepip` installation.

### Suggested commit

```text

```

## Task 9 — Update release sequencing

### Files

Inspect the existing release work first.

Likely:

- Modify: `.github/workflows/release.yml`
- Modify: `pyproject.toml`
- Modify: version-contract tests
- Modify: release documentation

### Product invariant

An extension release must never advertise an engine version that cannot actually be provisioned.

Therefore:

```text
Python package availability
        ↓
extension release considered usable
```

### Required release gates

Before declaring version `X.Y.Z` usable:

1. build sdist/wheel;
2. run package checks;
3. install package non-editably;
4. exercise canonical CLI path;
5. exercise extension bootstrap against that exact package candidate;
6. publish/rehearse through TestPyPI where practical;
7. perform extension-first render from a clean project;
8. only then approve production release.

### Version parity

Keep one release version across:

```text
quarto_needs.__version__
pyproject.toml
_extension.yml
managed runtime expected version
```

The packaging test must fail on drift.

### Published package verification

Once production publication exists, add a release-only test that performs a clean first render **without** `QUARTO_NEEDS_ENGINE_SOURCE`, proving the extension really provisions the published exact package.

Do not make ordinary pull-request CI depend on a package version that has not been published yet.

Suggested commit:

```text
ci: gate extension releases on managed-engine availability
```
