# Phase 5.5 — External service adapters

Status: **complete — planned scope delivered across ten slices plus explicit trust transitions, the apply step, and the caller-side retry policy. A read-only GitHub issue projection is implemented end to end: external identity, content-digest provenance, normalization into the same observation shape OSLC federation already uses, a bounded GET-only HTTP transport with rate-limit exhaustion distinguished from auth failures, a persistent content-addressed cache, conditional requests, bounded issue-list discovery, bounded multi-page traversal of that discovery, search-API discovery with the same bounded contract, reconciliation + import planning through OSLC's own source-agnostic contracts, explicit reviewer trust-state transitions, an apply step writing accepted plans into authored files with all-or-nothing preflight and post-write rollback, a caller-side rate-limit retry policy honoring the server's own retry facts, and a fully traced self-hosted example slice (STK-007 → SYS-008 → FUN-014…017 / NFR-007 → ADR-010 → SRC-GITHUB-HTTP / SRC-GITHUB-ISSUES → TC-020…024 → EVD-020…024) with five real pytest bindings in the attested evidence artifact — all exercised against the real GitHub API, including a real HTTP 304, a real list-then-fetch handoff, and a real two-page traversal across GitHub's rewritten Link targets. The rationale authoring form is now indexed by the parser too.**

Quarto-Needs treats every external service the same way it treats OSLC: as a read-only, provenance-preserving federation boundary around the canonical engineering graph, never a second semantic authority. Every imported object must preserve external identity, origin, digest/version, retrieval policy, and trust state — the same four guardrails `docs/ROADMAP.md` states for this phase, applied here to GitHub issues as the first external source.

## Why this reuses OSLC's identity model instead of a new one

`ExternalResourceIdentity` and `CachePolicy` (`src/quarto_needs/oslc_rm.py`) turned out to already be source-agnostic in practice: their fields (`resource_uri`, `service_provider_uri`, `digest`, `fetched_at`, `trust_state`, `etag`, `last_modified`) and validation (absolute-URI checks, `sha256:`-prefixed digest format, a fixed trust-state enum) encode nothing OSLC- or RDF-specific. `ExternalRequirementObservation` (`src/quarto_needs/oslc_reconcile.py`) is the same story: `identity`, `title`, `description`, `external_identifier`, and a free-form `attributes` bag is exactly the shape a normalized external issue needs too. `src/quarto_needs/github_issues.py` imports and reuses these types directly rather than defining parallel ones — the "one adapter, one contract" principle the migration adapters (Sphinx-Needs/Doorstop/StrictDoc) already established, applied here to federation instead of migration.

What was **not** reused as-is: `oslc_http.py`'s bounded transport (its media-type allowlist and cache-policy wiring are RDF/OSLC-specific). `src/quarto_needs/github_http.py` is instead a small, independent bounded transport for GitHub — same shape of guarantee (bounded bytes/time/redirects, same-origin redirect enforcement, request-only auth headers), different, `application/json`-only media-type check, and it does share `oslc_http.py`'s fully generic `HttpFetchPolicy` dataclass directly. Duplicating the ~150-line transport mechanics rather than reaching into `oslc_http.py`'s underscore-prefixed internals kept an already-shipped, heavily tested subsystem untouched while this one was still new.

`oslc_cache.py` turned out to be a different case: reading it closely, its persistence logic (content-addressed blob storage, atomic writes, digest verification, duplicate-observation rejection, freshness decisions) has exactly one OSLC-specific coupling — the manifest's `"schema"` field was hardcoded to the module-level `OSLC_CACHE_SCHEMA` constant rather than accepted as a parameter. That one hardcoded value was the only thing standing between "OSLC's cache" and "a cache for any content-addressed external representation with an `ExternalResourceIdentity`." `load_cache_manifest`, `write_cache_manifest`, `store_cached_representation`, `latest_cached_representation`, and `select_cached_representation` each gained an optional `schema: str = OSLC_CACHE_SCHEMA` parameter (every existing OSLC call site is unaffected, since the default reproduces the prior hardcoded behavior exactly); the GitHub adapter calls them with `schema="github-issues-cache-v1"`. This is deliberately the same fix already applied once this phase, to `SphinxNeedsMigrationPlan.tool`/`.schema` for the migration adapters: find the one hardcoded literal blocking reuse, parameterize it with a default that preserves every existing caller, and let a second source pass its own value — never fork the implementation. A new test (`test_cache_schema_is_a_parameter_not_a_hardcoded_oslc_constant`) proves the isolation this buys: a cache root written under one schema is never silently read back, or silently overwritten, under a different one. Error message wording inside `oslc_cache.py` still says "OSLC cache..." even when invoked for GitHub — a deliberately accepted, purely cosmetic imprecision in an internal exception string, not touched because rewriting it would have meant updating several existing tests' exact-message assertions for zero behavioral gain.

`oslc_rdf.py`'s JSON-LD/Turtle/RDF-XML normalization was not reached for at all — GitHub's REST API returns plain JSON, not RDF, so there was nothing there to generalize.

## Reconciliation and import planning: the slice that needed no new code

The roadmap expected a GitHub reconciliation step and a GitHub import-plan step, mirroring `oslc_reconcile.py`/`oslc_import_plan.py`. Reading those modules closely before building mirrors turned up the same fact the cache slice found: they are already source-agnostic. `reconcile_external_requirements` consumes `(snapshot, observations, bindings)` where observations are `ExternalRequirementObservation`s — which `parse_external_github_issue` already produces — and `build_oslc_import_plan` consumes `(snapshot, observations, reconciliation, directives)` with nothing OSLC-specific anywhere in the signature or the body. The identity bridge is the same explicit external-URI → canonical-ID binding map, never a heuristic over titles or identifiers; the import plan is the same non-mutating review artifact carrying create/update/ignore directives toward a future apply step.

So the honest deliverable of this slice is the *proof*, not a fork: every contract is pinned by tests against GitHub-shaped observations (`tests/test_github_reconcile.py`) —

- an issue number stays data even when it literally equals a canonical ID in the snapshot: without an explicit binding the observation is `unbound`, never heuristically matched (falsified: temporarily adding an identifier-matching heuristic to `reconcile_external_requirements` makes the test fail, alongside the OSLC suite's own equivalent test);
- an explicit **API-URI** binding (`https://api.github.com/repos/{owner}/{repo}/issues/{number}`) yields `matched` with informational-only differences, mutating neither side;
- a binding keyed by the issue's HTML URL (`https://github.com/...`) is rejected loudly ("bindings reference unobserved external URIs") — hand-built keys cannot silently mismatch the adapter's canonical URI construction;
- the full pipeline composes: fake-opener fetch → `parse_external_github_issue` → reconcile `matched`, with the observation digest still over the exact fetched bytes;
- import planning: a create directive on an unbound observation is `ready-create` (carrying id/type/status/title/body changes and the reviewed `target_path`), a create against an existing canonical ID is `blocked`, an update on a matched observation is `ready-update` with only the differing fields, a missing directive is `review-required`, and an ignore directive is `ignored` — every item carrying the observation's `source_digest`/`fetched_at` provenance.

Live-checked against `strictdoc-project/strictdoc`: a real observation (issue #2067) reconciled as `unbound` without a binding, `matched` with an explicit API-URI binding, planned `ready-create` and `ready-update` through the real contracts, and an HTML-URL binding key rejected exactly as the suite predicts.

The one accepted imprecision: plan artifacts still serialize with `"schema": "oslc-import-plan-v1"` and the class remains `OslcImportPlan` even when the items are GitHub observations. Unlike the cache case, no artifact is ever *read back* by schema here — the plan is an in-memory review artifact serialized once, and each item's `externalUri` already names its source — so a schema parameter would be ceremony without an isolation guarantee to justify it. If a future apply step persists plans for later consumption, that is the moment the schema parameter earns its place.

`oslc_query.py` was read but not reused: its member-parsing is built on `rdfs:member` containers and RDF node indexing, which has no equivalent in a plain JSON array response, so there was no shared *code* to converge on. What *is* deliberately mirrored is the same architectural boundary: `oslc_query.py`'s own design note observes that "a query container may include inline member data, but its response digest is not the digest of every member resource" — independent per-member retrieval is what makes reconciliation trustworthy. GitHub's issue-list endpoint is exactly this "inline member data" case (each list entry already carries the full issue body), and it would have been easy to treat that as good enough. `fetch_external_github_issue_list` deliberately does not: it returns issue *numbers* (discovery), never an `ExternalRequirementObservation` built from the list response's inline data. Getting a provenance-bound observation for a discovered number is a separate call to the already-existing `fetch_external_github_issue`, with its own independently-fetched digest/etag — the same query-then-observe split OSLC's `oslc_query.py`/`oslc_observe.py` enforce, arrived at independently by asking "would trusting this inline data violate the same principle OSLC already documented a reason not to?"

## What is implemented

- `github_issue_resource_uri(owner, repo, number)` — the deterministic GitHub REST API URL identifying one issue (`https://api.github.com/repos/{owner}/{repo}/issues/{number}`), used as `ExternalResourceIdentity.resource_uri`.
- `build_github_issue_identity(owner, repo, number, *, payload_bytes, fetched_at, trust_state="unverified", etag=None, last_modified=None)` — builds the identity from the *exact bytes actually fetched* (the digest is over `payload_bytes`, never a re-serialization of parsed fields), matching how OSLC's own provenance model works.
- `parse_external_github_issue(payload, *, identity)` — normalizes a raw GitHub issue JSON payload into an `ExternalRequirementObservation`. Validated against a real payload fetched live from `strictdoc-project/strictdoc`'s issue tracker, not only synthetic fixtures:
  - `number` (must be a real `int`, not a numeric string) → `external_identifier` (data only — never promoted into a canonical ID by this parser, the same non-negotiable boundary OSLC's own reconciliation enforces);
  - `title` (required, non-empty) → `title`;
  - `body` (`null` treated as empty) → `description`;
  - `state` (must be `"open"` or `"closed"`; anything else is rejected rather than guessed) → `attributes["state"]`;
  - `html_url`, `updated_at` (both required) → `attributes["htmlUrl"]` / `attributes["updatedAt"]`;
  - `labels` (a list of label objects; `name` extracted, sorted, deduplication left to the caller) → `attributes["labels"]`;
  - a payload carrying a `pull_request` key is rejected outright (`GitHubIssueError`) — GitHub's issues endpoint returns pull requests too, and treating one as a requirement-shaped issue would misrepresent a fundamentally different artifact.
- `fetch_github_resource(uri, *, fetch_policy, auth_headers, if_none_match=None, if_modified_since=None, opener)` (`src/quarto_needs/github_http.py`) — bounded, GET-only HTTP: byte limit (declared `Content-Length` and actual bytes read both enforced), timeout, a fixed redirect budget with same-origin enforcement (an `Authorization` header cannot leak to a redirect target on another host), `401`/`403` → `authentication-required`, `404` → `not-found`, and an `application/json`-only media-type check. `auth_headers` is a request-only input (e.g. `{"Authorization": "Bearer <token>"}`) matching OSLC's own "authentication headers are never persisted" contract; it cannot override the transport's own `Accept`/`User-Agent`. `if_none_match`/`if_modified_since`, when supplied, are sent as `If-None-Match`/`If-Modified-Since`; a `304` response returns `GitHubFetchResult(payload=None, etag=..., last_modified=...)` rather than being run through the `application/json` media-type check or the byte-limit reader a body-carrying response gets. Tested exclusively against a fake, injectable opener (no live network call in the committed suite, mirroring OSLC's own "network-free by design where provider behavior is simulated"), with the cross-origin-redirect and byte-limit checks specifically falsified rather than only asserted.
- `fetch_external_github_issue(owner, repo, number, *, fetched_at, cache_root=None, cache_policy=CachePolicy(max_age_seconds=300), ...)` — composes the transport, identity, and parser above into one read-only fetch-and-normalize call. Caching is opt-in: pass `cache_root` and a fresh cached representation is returned without touching the network at all; a stale entry sends a conditional request built from that entry's own `etag`/`last_modified` — a `304` reuses the cached body under a refreshed identity (new `fetched_at`, same digest) instead of re-downloading it, a `200` replaces it entirely; a cold cache (no entry at all) sends a plain, unconditional GET. Stored under `GITHUB_ISSUES_CACHE_SCHEMA = "github-issues-cache-v1"`. Run live against `strictdoc-project/strictdoc` on GitHub — issue #3164 (real `ETag`/`Last-Modified`/digest came back correctly), issue #500 to confirm pull-request rejection fires against a real PR returned by the same endpoint, a real two-call cache run measuring ~0.4s live / 0.0s cache hit, and — with `max_age_seconds=0` to force staleness — a real second call whose conditional request received an actual HTTP `304` from GitHub with the correct `If-None-Match`, reusing the cached body and refreshing only `fetched_at`.
- `fetch_external_github_issue_list(owner, repo, *, fetched_at, state="open", per_page=30, page=1, ...)` — one bounded, GET-only page of `GET /repos/{owner}/{repo}/issues`, returning `GitHubIssueListResult.issue_numbers`/`.pull_request_numbers` (both explicit — a pull request in the list is reported, not silently mixed in with issues or silently dropped) plus the list response's own digest/`fetched_at`. Discovery only: it never builds an `ExternalRequirementObservation` from a list entry's inline data (see above); each discovered number needs its own `fetch_external_github_issue` call for a provenance-bound observation. Run live against `strictdoc-project/strictdoc` — a real 5-issue page split correctly into 3 issues and 2 pull requests, and one discovered number successfully handed off to a real `fetch_external_github_issue` call.
- `fetch_external_github_issue_list_pages(owner, repo, *, fetched_at, state="open", per_page=30, max_pages=1, ...)` — bounded multi-page traversal of that same list, following GitHub's own `Link: rel="next"` target across pages up to an explicit `max_pages` budget (default 1: no traversal unless the caller asks for one). The design facts worth recording:
  - `truncated` is an honest report, not a guess: it is set exactly when the budget runs out while GitHub still offers a next page, so "stopped at budget" is never conflated with "the list ended".
  - A present-but-malformed `Link` header raises (`GitHubIssueError`) rather than silently reading as "no next page" — a silent stop would misreport a truncated traversal as complete.
  - The server-provided next URL is followed within the request's **origin only** (`fetch_external_github_issue_list` never followed URLs at all, so this guard is new surface): GitHub legitimately rewrites `/repos/{owner}/{repo}` to `/repositories/{id}` (plus an `after=` cursor parameter) in its own Link targets — discovered live — so path equality is deliberately *not* required, but a cross-origin next is rejected, the same boundary the transport already enforces for redirects.
  - The list endpoint's own documented filters (`labels`, `since`, `sort`, `direction`) joined `state` as explicit, validated URI parameters on both the single-page and multi-page calls. These are the list endpoint's parameters, never the separate search API.
  - Aggregates (`issue_numbers`/`pull_request_numbers`) are deduplicated unions, while each page's own `GitHubIssueListResult` keeps its raw per-page truth; the traversal stays discovery-only (numbers, never observations).
  - Run live against `strictdoc-project/strictdoc`: a real two-page traversal (8 issues / 2 pull requests across pages, page 2 served from `https://api.github.com/repositories/263988764/issues?...&after=<cursor>` — the rewritten path exercised for real), honest truncation at `max_pages=1`, one page-2-discovered number (#3115) fetched as a full provenance-bound observation, and a live `labels=["documentation"]` page finding issue #2067.- rate-limit classification in the transport (`github_http.py`) — GitHub's rate limiting is no longer flattened into the generic auth/availability errors:
  - a `403` carrying `X-RateLimit-Remaining: 0` (GitHub's primary-exhaustion shape; header names verified against real responses) and any `429` (GitHub uses it for both primary and secondary limits) raise `GitHubRateLimitError` (code `rate-limited`), a *subclass* of `GitHubTransportError`, so existing callers catching transport errors keep working while rate-limit-aware callers can retry informed;
  - the error carries the server's retry facts — `retry_after_seconds` (from `Retry-After`, integer-seconds form) and `rate_limit_reset_epoch` (from `X-RateLimit-Reset`) — and the transport never sleeps on its own; deciding what to do with a rate limit is the caller's policy, not the transport's;
  - a `403` *without* the exhaustion header keeps its existing `authentication-required` classification (a forbidden resource is an auth problem, not a rate limit), and a non-integer `Retry-After` raises `invalid-response` rather than being silently ignored;
  - falsified both ways: removing the `403`-exhaustion condition makes the exhaustion test fail back into `authentication-required`; removing the `429` condition fails three tests. Live-checked that normal (non-exhausted) requests are untouched and that the real `/rate_limit` endpoint's `remaining`/`reset` semantics match what the error reports; a real exhaustion was deliberately **not** triggered, since it would consume the shared-IP hourly quota — the exhaustion shapes are fake-opener tests seeded with real header names and values.
- `fetch_external_github_issue_search` / `fetch_external_github_issue_search_pages` (`github_issues.py`) — bounded discovery over the search endpoint, the last of the three read-only discovery surfaces (single list page, list traversal, search):
  - the search envelope is validated explicitly — non-negative integer `total_count`, boolean `incomplete_results`, an `items` array (whose entries reuse the list parser's issue/pull-request separation); items stay inline data, never observations;
  - scoping is the caller's explicit qualifier string (`repo:owner/name is:issue label:...`) — the adapter never guesses scoping, and one URI always identifies exactly one bounded page of one explicit search (sort restricted to the endpoint's documented set);
  - the multi-page traversal is the *same machine* as the list's, extracted into one shared bounded loop (`_traverse_discovery_pages`: origin-validated next targets, honest `truncated`, malformed Link headers raise) rather than a fork; the search result adds `total_count` (query-level, from the first fetched page) and `incomplete_results` (conservative union — true if any fetched page reported it), so a possibly incomplete search is never presented as complete;
  - the search endpoint counts against GitHub's separate search rate-limit class; a 403/429 there raises the same distinguished `GitHubRateLimitError` as everywhere else;
  - falsified: removing the envelope validation accepts a missing/non-integer `total_count`; forcing the `incomplete_results` union to `False` misreports a flagged page as complete. Live-checked against `strictdoc-project/strictdoc`: a real query (`repo:... is:issue documentation`, `total_count=81`), a real two-page traversal with honest truncation at `max_pages=2`, and one discovered number (#577) fetched as a full provenance-bound observation.
- explicit trust-state transitions (`external_trust.py`) — `apply_trust_decision` consumes an immutable, substantive reviewer decision (`action` ∈ trust/reject/mark-stale/reset, plus `decided_by`/`reason`/`decided_at`, all required non-empty) and returns a *new* `ExternalRequirementObservation` with the transitioned trust state plus an auditable `TrustDecisionRecord`; the transitions form a closed `(from, action) → to` allowlist — a rejected observation must pass an explicit `reset` before it can ever be trusted again; the input observation is never mutated and the digest/`fetched_at` carry over unchanged (a trust decision is the reviewer's judgement, not a re-fetch); the transitioned state flows into the unchanged reconciliation contract (rejected blocks, reset unbinds, trust matches). Falsified by bypassing the allowlist.
- an apply step (`import_apply.py`) — the first write path downstream of the reviewed plan. It inherits the migration apply's safety contracts (all-or-nothing, atomic per-file writes, post-write re-scan with rollback on any error-severity finding, idempotence through refusal) and extends them to updates: every applicable item (`ready-create`/`ready-update`) is preflighted against a fresh scan — a create whose canonical ID already exists refuses (that refusal *is* the idempotence contract), an update whose plan `from` values no longer match the authored file refuses as stale, and an update whose target file differs from where the object is actually authored refuses the mismatch. Blocks are rewritten in place with their metadata preamble preserved; non-applicable dispositions (blocked, review-required, ignored, no-change) are reported as skipped with the plan's own reason, never half-applied. Falsified by removing the staleness preflight and the create-exists preflight.
- self-hosted example integration (`examples/quarto-needs/interoperability.qmd` + its pt-BR twin) — the GitHub adapter is now a fully traced slice of the self-hosted engineering model, mirroring the OSLC slice's structure:
  - `STK-007` → `SYS-008` → `FUN-014` (identity/projection without canonical identity) / `FUN-015` (bounded cached conditional transport) / `FUN-016` (bounded discovery and traversal) / `FUN-017` (reconciliation through the shared explicit-binding contracts) / `NFR-007` (bounded, provenance-preserving, rate-limit-explicit) → `ADR-010` (read-only, bounded, discovery-separated; confirms via TC-020/021/022/024) with `COMP-GHISSUES`, `IF-006`, `RISK-012` (unbounded pagination / silent truncation / rate-limit blindness), and source modules `SRC-GITHUB-HTTP`/`SRC-GITHUB-ISSUES`;
  - five test cases (`TC-020`…`TC-024`) bind to real pytest nodeids and five evidence objects (`EVD-020`…`EVD-024`) point at the attested artifact; the tests carry matching `requirement`/`quarto_need_test_case` markers and all five nodeids joined `make evidence-self-example`, so the machine evidence now attests 16 linked tests against the graph (evidence check cross-validates markers ↔ model, which caught one real drift during authoring: `NFR-007` initially omitted `TC-022` from its `verified-by` while the pagination test carried the `NFR-007` marker);
  - `FUN-017`'s `implemented-by` deliberately includes `COMP-OSLC`: reconciliation/import planning run through the OSLC subsystem's modules, so the model itself records the reuse this phase discovered;
  - the pt-BR page mirrors all 23 objects with identical semantic signatures (verified by the parity regression) and the page's traceability chains and per-tag need-tables cover both languages.

- a caller-side rate-limit retry policy (`github_retry.py`) — the decision layer the transport deliberately omitted: `wait_before_attempt` turns a `GitHubRateLimitError` into a wait (server's `Retry-After` first, then `X-RateLimit-Reset` when the caller supplies a clock, then bounded exponential backoff; everything clamped to `max_wait_seconds`) or `None` to give up, and `fetch_with_retry` wraps any zero-argument fetch with that policy — sleeping only between rate-limit retries, re-raising the server's own error (facts intact) when the attempts run out, and propagating every other failure immediately. `max_attempts` counts total attempts including the first. Falsified by removing the `Retry-After` honoring.

## What was learned

The planned 5.5 scope is complete. The through-line of the whole phase: reuse the source-agnostic contract when one exists (identity, cache, observation, reconciliation, import plan — each discovered by reading before building), fork only when the transport semantics genuinely differ (a JSON transport beside the RDF one), keep discovery and observation separate, make every failure mode a distinguished fact (auth, availability, rate limit, truncation, staleness), and gate the single write path behind explicit reviewer artifacts end to end.

## What is intentionally not implemented yet

Nothing is left deferred from the planned scope. Natural follow-ons, each its own reviewed slice if ever needed: the OSLC adapter could adopt the same trust-transition and apply contracts (they are source-agnostic today), and GitHub-scoped commands could grow a CLI surface consuming fetch/retry policy directly.

None of that is guessed at here — each is deferred exactly because OSLC took each as its own reviewed, independently tested slice, and there is no reason to expect a GitHub-specific query/reconciliation/import-plan design to be simpler or safe to rush.
