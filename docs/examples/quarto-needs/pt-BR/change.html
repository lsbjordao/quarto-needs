10  Mudança: do histórico de versões ao impacto de engenharia

A engenharia de requisitos não termina quando o primeiro grafo coerente é aprovado. A pergunta difícil é o que uma mudança significa para o restante do sistema. Por isso, o Quarto-Needs trata comparação como um fluxo de engenharia, e não como um simples diff textual do Git.

Este capítulo usa uma mudança real do Quarto-Needs, em vez de um exemplo hipotético: o controle do índice lateral da página que foi corrigido depois que o botão no estado expandido passou a se sobrepor ao próprio índice.

10.1 A mudança histórica do produto

A correção original de UI é o commit ba4655d72d3b0e9fc926a2d31c77c7705efd00b2 (fix: improve graph dark theme and TOC toggle), cujo parent é 77eaaf91d0127fffe974b449e5ee9718861da552.

Esse commit alterou _extensions/quarto-needs/margin-sidebar.js: o botão expandido era posicionado subtraindo apenas metade de sua largura do limite do índice. A correção introduziu um espaçamento explícito de 8 px e passou a subtrair a largura completa do botão, mantendo o controle inteiramente fora do índice.

antes: rect.left - button.offsetWidth / 2
 depois: rect.left - button.offsetWidth - gap
                              onde gap = 8

Esse é o gatilho no histórico do código deste caso. Naquele commit histórico, porém, o modelo de engenharia autocontido mais recente ainda não continha a cadeia completa FUN-009 → ADR-007 → SRC-MARGIN-SIDEBAR → TC-014 → EVD-014. Um tutorial profissional não deve fingir o contrário.

10.2 O corte vertical modelado

O comportamento do produto agora está explicitamente modelado:

SYS-002  Publicar o modelo de engenharia como documentação Quarto
   ↓ derives-from
FUN-009  Recolher o índice lateral sem ocultar a navegação
   ↓ addressed by
ADR-007  Controle persistente como aprimoramento progressivo
   ↓ applies to
COMP-EXTENSION
   ↓ superfície de implementação
SRC-MARGIN-SIDEBAR  _extensions/quarto-needs/margin-sidebar.js
   ↓ verificação
TC-014  Regressão de posicionamento do controle do índice lateral
   ↓ evidenced-by
EVD-014 Evidência de máquina da usabilidade do índice lateral

TC-014 está vinculado ao nó pytest real tests/test_graph_assets.py::test_margin_sidebar_toggle_stays_entirely_outside_page_toc. Ele verifica o espaçamento explícito de 8 px, o deslocamento pela largura completa do botão, a persistência e o comportamento temporário de fullcontent.

10.3 Um intervalo Git semântico reproduzível

Para demonstrar análise de engenharia Git-native com modelos válidos dos dois lados, este repositório contém uma clarificação canônica posterior de FUN-009:

base  ba69e62cf9ba4a0fb186a28e6e87649c1462f2dd
head  53dc04bf6bdd98a2f8143964684d20464d6264f6

O head esclarece na justificativa do requisito que o posicionamento é comportamento de engenharia protegido por um contrato executável de regressão, e não estilização decorativa incidental. Identidades e vínculos de rastreabilidade já existem nos dois estados, portanto esse intervalo pode ser materializado e analisado de forma determinística.

Defina-o uma vez no shell:

RANGE=ba69e62cf9ba4a0fb186a28e6e87649c1462f2dd..53dc04bf6bdd98a2f8143964684d20464d6264f6

10.4 Etapa 1 — inspecionar o diff de engenharia

quarto-needs --root examples/quarto-needs \
  diff --git "$RANGE"

Para consumidores de máquina:

quarto-needs --root examples/quarto-needs \
  diff --git "$RANGE" --format json

Diferentemente de um patch textual, o resultado identifica o objeto de engenharia alterado (FUN-009) e os campos autorais que mudaram. Ambos os refs são extraídos com git archive e analisados de forma independente; o working tree não é trocado nem modificado.

O Quarto-Needs usa o timestamp do commit head como reference epoch comum aos dois estados materializados. Isso evita que o mesmo intervalo Git produza resultados sensíveis a data diferentes apenas porque foi analisado em outro dia.

10.5 Etapa 2 — inspecionar caminhos explícitos de impacto

quarto-needs --root examples/quarto-needs \
  impact --git "$RANGE"

A análise de impacto percorre a união dos dois grafos de engenharia seguindo as direções canônicas de impacto do catálogo. O resultado é um conjunto de caminhos explícitos, não uma pontuação sintética de risco.

Neste caso, a atenção de revisão a jusante alcança o lado de verificação/evidência da cadeia. O resultado exato é calculado a partir do grafo, e não codificado como regra específica deste exemplo.

10.6 Etapa 3 — derivar rastreabilidade suspeita

quarto-needs --root examples/quarto-needs \
  suspect --git "$RANGE" --format json

Uma claim suspeita é estado derivado, e não um flag persistido suspect=true. Cada claim carrega uma testemunha:

origem + mudança
    ↓
caminho explícito de relações
    ↓
objeto afetado + papel semântico

Assim, o revisor vê não apenas que um teste ou evidência precisa de nova atenção, mas por que se tornou suspeito e por quais relações.

10.7 Etapa 4 — gerar o relatório de engenharia da pull request

quarto-needs --root examples/quarto-needs \
  pr-report --git "$RANGE" --format markdown

O relatório agrupa objetos alterados e afetados por papel semântico e inclui:

  • requisitos e ADRs alterados;
  • elementos de arquitetura e módulos-fonte afetados;
  • testes e evidências a jusante;
  • evidência suspeita/obsoleta;
  • findings adicionados/removidos;
  • regressões de gates;
  • caminhos explícitos de impacto.

A projeção JSON está disponível com --format json.

10.8 Etapa 5 — projetar a mesma análise no CI do GitHub

A projeção GitHub não chama APIs do GitHub e não é dona da semântica de engenharia. Ela converte o relatório canônico da PR em superfícies apropriadas para CI.

Markdown para step summary:

quarto-needs --root examples/quarto-needs \
  github-report --git "$RANGE" --format markdown

Annotations de workflow:

quarto-needs --root examples/quarto-needs \
  github-report --git "$RANGE" --format annotations

Projeção estruturada do check:

quarto-needs --root examples/quarto-needs \
  github-report --git "$RANGE" --format json

O CI do repositório usa essas mesmas superfícies em pull requests: baixa o histórico Git completo, recebe os SHAs de base/head do evento da PR, acrescenta o resumo de engenharia ao GITHUB_STEP_SUMMARY e emite annotations escapadas no log do workflow.

10.9 Por que duas referências históricas são úteis

Este exemplo preserva deliberadamente duas histórias verdadeiras:

  1. Histórico da implementação do produto — 77eaaf91…ba4655d7, onde o bug de sobreposição no JavaScript foi realmente corrigido.
  2. Histórico executável do modelo de engenharia — ba69e62c…53dc04bf, onde existe um grafo autocontido completo e válido nos dois lados e a mudança pode se propagar por requisitos, decisões, implementação, testes e evidências.

Misturar essas duas histórias deixaria a documentação aparentemente mais simples, porém menos correta. O Quarto-Needs mantém a proveniência explícita.

10.10 Perguntas para revisão

Uma boa revisão de mudança deve conseguir responder:

  • Qual preocupação de stakeholder/sistema continua motivando o requisito alterado?
  • Quais ADRs passam a ser candidatos a reconsideração?
  • Quais componentes lógicos e módulos-fonte implementam a obrigação afetada?
  • Quais casos de verificação precisam ser reexecutados ou alterados?
  • Quais evidências ficaram suspeitas, obsoletas ou precisam ser regeneradas?
  • Quais quality gates ou findings mudaram?
  • Qual caminho exato no grafo justifica cada claim de revisão a jusante?

É aqui que requirements-as-code se torna mais do que armazenar requisitos em Git: o próprio grafo versionado participa do raciocínio de engenharia.
