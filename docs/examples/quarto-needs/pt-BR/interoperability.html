8  Interoperabilidade: federar sem abrir mão do modelo canônico

O Quarto-Needs trata intercâmbio e federação como projeções e adaptadores ao redor do grafo canônico de engenharia. Padrões externos podem transportar, descrever ou descobrir requisitos, mas não se tornam uma segunda autoridade semântica.

stakeholder-need approved

As equipes precisam trocar e descobrir requisitos por padrões estabelecidos preservando identidade canônica, proveniência, confiança e semântica explícita de perdas.

STK-007 · Equipes de engenharia precisam de requisitos vinculados ao estado vivo do rastreador sem importá-lo

stakeholder-need approved

As equipes precisam de visibilidade somente leitura do estado de issues do GitHub — descoberta, travessia limitada e observações normalizadas — enquanto o GitHub permanece uma fonte externa cuja identidade, proveniência e limites de confiança ficam fora do grafo canônico.

interoperability github issues tracker
Referências inversas
Origem de
SYS-008 — Federar issues do GitHub como observações somente leitura com proveniência

SYS-008 · Federar issues do GitHub como observações somente leitura com proveniência

system-requirement approved high

O Quarto-Needs deverá buscar issues do GitHub por HTTP limitado e somente GET, normalizá-las na mesma forma de observação externa que a federação OSLC usa, descobrir e percorrer páginas de listagem de issues dentro de orçamentos explícitos, e reconciliar issues observadas por vínculos explícitos de URI-de-API para ID canônico — nunca promovendo números de issue, URLs HTML ou dados inline de listagem a identidade canônica.

interoperability github issues provenance

Justificativa

Issues do GitHub carregam estado relevante para a engenharia, mas o rastreador é mutável, paginado, sujeito a limites de taxa, e mistura pull requests em suas listagens de issues — a federação, portanto, precisa de orçamentos limitados, proveniência exata em nível de byte, e separação explícita entre descoberta e observação.

ADR-010 · Manter o caminho de issues do GitHub somente leitura, limitado e com descoberta separada

architecture-decision accepted 2026-08-31

Contexto e problema

A API de issues do GitHub retorna pull requests junto com issues, reescreve URLs de paginação de /repos/{owner}/{repo} para /repositories/{id} com parâmetros de cursor, inclui dados completos inline nas respostas de listagem e aplica rate limit com 403/429. Tratar qualquer um desses como dados canônicos de requisitos, seguir paginação sem orçamentos ou achatar rate limits em erros genéricos apagaria a fronteira de confiança.

github federation read-only security

Resultado da decisão

A federação GitHub é um adaptador somente leitura composto de um transporte JSON limitado com classificação de rate limit, um cache endereçado por conteúdo opcional com requisições condicionais, normalização de issues que rejeita pull requests, descoberta e travessia multi-página limitada que permanecem apenas com números, e reconciliação/planejamento de importação pelos contratos OSLC inalterados. Dados de listagem nunca são promovidos a observações; destinos de paginação são checados por origem; rate limits levantam um erro distinto que informa o retry.

Confirmação

TC-020 exercita fetch-composição-normalização com proveniência dos bytes exatos; TC-021 exercita o caminho de reuso 304 com requisição condicional; TC-022 exercita travessia limitada pelos destinos de paginação reescritos do GitHub com truncamento honesto; TC-024 exercita a classificação de esgotamento de rate limit com formatos reais de cabeçalhos.
